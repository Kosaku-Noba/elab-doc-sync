# 同期エンジン

→ [API リファレンス](06_API_REFERENCE.md) | [性能仕様](08_PERFORMANCE.md)

## 状態判定

`EachDocsSyncer.inspect()` をstatus・push・pullで共用します。読み取りだけを行い、次の状態を返します。

| 状態 | 意味 | 通常のpull |
|---|---|---|
| 最新 | 前回から変更なし | スキップ |
| 送信待ち | ローカルの本文・設定・画像・添付が変更された、`links` に未作成のリンクがある、または eLabFTW が削除した `<…>` が未解消 | ローカル編集を保持 |
| 取得待ち | リモートの本文・タイトル・カテゴリ・タグ・添付情報が変更された | バックアップ後に取得 |
| 競合 | 両側に変更あり | 3-way マージ（両側が同じ箇所を変えた場合はマーカー） |
| 競合マーカーあり | ローカル文書に esync の競合マーカーが残っている | 停止（push は `--force` でも停止。`pull --force` は上書き） |
| 基準情報なし | 安全な比較に必要な保存情報がない | 既存ファイルを上書きしない |
| 未追跡 | ファイルはあるが紐付けなし | 明示ID取得時に同名ファイルを保護 |
| ローカル削除 | 紐付け先のローカル文書がない | 明示pullで再取得可能 |
| リモート削除 | APIが404を返した | 自動再作成しない |
| 確認失敗 | 認証・通信・状態情報のエラー | 停止 |

`status` はさらに「作成結果不明」「同期未完了」を表示します。

## pullのマージ

同期が完了するたびに、その時点のローカルの本文を `{filename}.synced` に保存します（`diff` で「ローカルの変更」を表示するため）。ただし pull でマージしたときは更新しません。マージ結果は未送信のため、その後の `diff` の「ローカルの変更」には、取り込んだ eLabFTW 側の変更も含まれます。また、その時点の eLabFTW の本文を pull と同じ形式（画像は `images/`、文書間リンクはローカルの相対パス）に変換して `{filename}.base` に保存し、マージの基準にします。ローカルの文書が基準と変換上の違いだけで異なる箇所（例: push 元の画像パス）は、ローカル側の変更として扱われるため、マージ後もローカルの記述が残ります。

マージ後は eLabFTW 側の状態と基準本文を更新し、ローカル側の本文・画像・添付のハッシュは更新しません。そのため、マージ結果とローカルの画像の編集は次の push で送信されます。設定（タグ・カテゴリ・本文形式）のハッシュは、未送信の設定変更があるときだけ残します。ないときは現在のファイル名で記録し直すため、eLabFTW で変わったタイトルを取り込んでも、push が設定のタグ・カテゴリを送り直してリモートの変更を戻すことはありません。

## pushの順序

1. 除外状態・紐付け・未完了記録を読み、曖昧なリネームを拒否する。
2. 既存記事とローカルの状態を確認する。認証エラー等を不存在扱いしない。競合マーカーが残る文書は送信しない。
3. 設定のカテゴリ名をターゲットごとに 1 回 ID に解決する。解決できなければ、カテゴリの設定が必要な文書（新規作成、設定・タイトル・本文形式の変更、`--force`、同期再開）だけを、eLabFTW を変更せずにスキップする。
4. 新規記事はPOST前に作成記録を書き、取得したIDを本文更新より先に保存する。
5. 全IDを使って文書間リンクを変換する。同じホストの他ターゲットの文書へのリンクも、リンクのパスで解決する。画像・動画・ファイルリンクをアップロードし、指定の本文形式で送る。PATCH 直後に保存された本文を未完了記録に残す（eLabFTW が保存時に本文を書き換えても再開できるように）。
6. 必要なタグ・カテゴリ・`links` のリンク・添付を同期する。失敗した文書は完了扱いにしない。`links` の追加だけが必要な文書では、タグ・カテゴリを再適用しない。
7. 文書の同期がすべて成功したら、同じ名前で差し替えた画像・動画・ファイルの古い版のうち、現在の本文から参照されていないものを削除する。削除に失敗した場合は警告を出して古い版を残す。削除の途中で処理が止まった場合は、次の push で再開する。
8. 成功した文書の状態を保存して未完了記録を解除する。`body_format: md` で eLabFTW が本文の `<…>` を削除していれば警告し、失敗として数える。失敗件数は終了コードにも反映する。

差し替え以外で本文から参照されなくなったアップロードは自動削除しません。`--prune-attachments` は別途明示する削除操作です。

## 文書間リンクの変換

同期済みの `.md` ファイル同士のリンクは、push 時に eLabFTW の記事 URL へ、pull 時にローカルのパスへ変換します。

```
push: [セットアップガイド](./setup.md)
  → [セットアップガイド](https://elab.example.com/database.php?mode=view&id=42)
pull: [セットアップガイド](https://elab.example.com/database.php?mode=view&id=42)
  → [セットアップガイド](../docs/setup.md)
```

- 対象は `.md` ファイルへのリンクだけ（画像、外部 URL、アンカーリンクはスキップ）。フラグメント（`#section`）は保持する
- 別のターゲット（`docs_dir`）の文書へのリンクも変換する。接続先のホストが同じターゲットに限る
- `%E6...` のように URL エンコードされたファイル名のリンクも変換する
- リンク先が同期済み（mapping に存在する）場合だけ変換する。未同期のリンクはそのまま残る
- pull 時のローカルリンクは、リンク先がその PC で置かれている場所（サブディレクトリを含む）への相対パスにする。別の PC や別のディレクトリ構成でも使える
- pull でリンク先を後から取得した場合、取得済みでローカル未編集の文書に残る記事 URL もローカルのパスに更新する。`pull --id` や `--target` で指定した文書に限らず、設定にある全ターゲットの文書が対象（変更前の内容はバックアップされ、`esync restore` で戻せる）。ローカルで編集中の文書は変更しない
- 接続先（`url`）を変える前に同期した文書の紐付けは、保存済みの同期状態から接続先の違いを確認できる場合、リンクの解決に使わない。同期状態の記録がない旧形式の紐付けは接続先を判定できないため、そのまま使う

## 保存情報

`id_file` の親ディレクトリに `mapping.json`、`excluded.json`、`pending.json` と文書ごとの状態ファイルを置きます。

- `*.state.json`: 前回のローカル本文・画像/添付・設定ハッシュ、接続先（`server`・`entity`・`profile`・`team`）、本文形式、リモートの比較情報（`remote`）、張り終えたリンク（`links`、`links` を設定したターゲットのみ）。
- `*.base`: 前回同期時の eLabFTW の本文（pull と同じ Markdown 形式。`body_format: md` では HTML エスケープした形で保存）。pull のマージ基準。
- `*.synced`: 前回同期時のローカルの本文。`diff` の「ローカルの変更」の比較元。
- `pending.json`: 本文更新後に止まった同期（再開用）。
- `excluded.json`: `esync rm` で追跡解除したファイル名。
- `*.hash` / `*.remote_hash` / `*.meta_hash` / `*.assets_hash`: 旧状態からの移行・互換用情報。
- `.elab-sync-operations/`: 作成要求の記録。ローカル復元で消さない。

状態保存は同じディレクトリの一時ファイルをfsyncしてから置換します。複数の状態ファイルを変更するローカル操作は、バックアップと復旧記録で保護します。CLIの書き込み操作にはプロジェクト単位のプロセスロックを使います。

## pullの順序

1. 明示されたターゲット・既存紐付け・タグ等から接続先と保存先を決める。複数接続先で同じIDが追跡されている場合はターゲット指定を要求する。
2. 本文・タイトル・添付情報と前回状態を比較する。
3. ローカル編集、ファイル名衝突、保存先外へのパスを確認する。
4. 変更対象ディレクトリと状態をバックアップする。
5. HTML 本文は Markdown へ変換し、Markdown 本文は eLabFTW が保存時に付けた HTML エスケープ（`&gt;`・`&amp;` など）を戻す。画像・添付を取得する。両側が変更した文書は `.base` を基準に 3-way マージする。
6. 文書を保存し、必要なら旧名を削除して紐付けと同期状態を保存する。

画像・添付の取得失敗は成功扱いにしません。部分的なローカル変更があれば復旧用IDを表示し、restoreまで次の書き込みを停止します。

詳細は [移行と復旧](13_MIGRATION_V1.md) を参照してください。
