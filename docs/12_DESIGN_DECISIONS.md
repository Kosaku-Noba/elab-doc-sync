# 設計判断記録

→ [要求仕様](10_REQUIREMENTS.md) | [テスト仕様](11_TEST_SPEC.md)

## v1.0での変更

本文・添付・設定のどれかが失敗した文書を同期完了として記録しません。タグ・カテゴリの失敗もCLIの部分失敗として扱い、再実行で再試行します。通常のpushでは変更のないローカルメタデータを再適用せず、pull後にリモートのカテゴリ・タグを不用意に戻さないようにします。

ローカル変更にはバックアップと復旧記録、状態保存には原子的置換、CLI書き込み操作にはプロジェクト単位のロックを導入します。POST結果不明時は自動再作成せず、list/linkで解決します。以降は旧版の判断記録で、v1.0との差分は本節と [同期エンジン](07_SYNC_ENGINE.md) を優先します。

## 1. FR-15 タグ・メタデータ管理

### 1.1 タグ同期方針: 追記のみ

push 時の YAML `tags` 設定は **追記のみ** で動作する。リモートに存在するが YAML に記載のないタグは外さない。

**理由:**
- eLabFTW 上で手動付与されたタグや他システム由来のタグを保護する
- 「完全置換」は破壊的であり、事故コストが高い
- タグを外したい場合は `esync tag remove` で明示的に操作する

### 1.2 メタデータ保全方針

`get_metadata()` は eLabFTW の metadata フィールドが null・不正 JSON・非 dict の場合に空 dict を返す。

**理由:**
- 不正な状態のデータを無理にパースするより、安全なデフォルトを返す方が堅牢
- `metadata set` 時に `get_metadata_raw()` で生データを確認し、読めない場合は警告を表示

### 1.3 タグ同期の失敗の扱い

タグ同期（`_sync_tags`）は本文更新の後に実行する。失敗しても送信済みの本文は戻さないが、v1.0 以降はその文書を同期完了として記録せず、CLI の部分失敗（終了コード 1）として扱い、次の push で再試行する（v0.x では best-effort として成功扱いにしていた）。

**理由:**
- タグ API の一時障害で本文の送信までやり直す必要はない
- 一方、成功扱いにすると設定のタグが付かないまま「最新」になり、気づけない

## 2. FR-16 ステータス管理

### 2.1 ステータス ID 指定方式

ステータスは eLabFTW のチーム設定で定義される ID で指定する。名前指定は非対応。

**理由:**
- ステータス名はチームごとに異なり、名前→ID の解決にはチーム ID が必要
- シンプルさを優先し、ID 直接指定とした

### 2.2 一括更新の安全策

`entity-status set` は複数エンティティが対象の場合、確認プロンプトを表示する。`--id` で単体指定も可能。

## 3. FR-22 接続プロファイル

### 3.1 設計方針

複数の eLabFTW サーバーや異なるチームアカウントに接続するための仕組み。

**実装:**
- `profiles` セクションに名前付きで接続情報を定義
- 各ターゲットで `profile: <name>` を指定して使い分け
- `elabftw` セクションとの後方互換: `elabftw` は暗黙の `default` プロファイル

**理由:**
- 別チームの eLabFTW にも投稿したいユースケースへの対応
- 既存の `elabftw` セクション形式を壊さない後方互換

### 3.2 CLI 操作

`esync profile add/remove/list` で YAML の profiles セクションを直接操作する。

## 4. FR-23 Pull 自動振り分け

### 4.1 スコアリングロジック

複数ターゲットが存在する場合、リモートエンティティのメタデータとターゲット設定をマッチングする。

| 条件 | スコア |
|---|---|
| `title_pattern` (glob) マッチ | +10 |
| `category` 一致 | +10 |
| `tags` 包含率 | 最大 5 + 特異性ボーナス |

**理由:**
- タイトルパターンとカテゴリは明確な意図の表れなので高スコア
- タグは部分一致でも有用だが、曖昧さがあるため重み付けを抑制
- 全ターゲットに共通するタグは特異性が低いとみなす

### 4.2 --auto フラグ

スコアリングで最高スコアのターゲットを自動選択する。対話プロンプトを省略したい CI/スクリプト向け。

### 4.3 新規ターゲット自動追記

マッチするターゲットが見つからない場合、リモートのメタデータ（entity/tags/category）から新しいターゲット定義を `.elab-sync.yaml` に追記する。

## 5. FR-24 添付ファイル

### 5.1 設計方針

`attachments_dir` に置いたファイルを push 時に eLabFTW にアップロードする。画像（Markdown 中の `![](...)` 参照）とは別枠。

**理由:**
- PDF・CSV・Excel 等を Markdown 本文とは独立して管理したいケースへの対応
- `attachments_pattern` で不要ファイルを除外可能

### 5.2 prune-attachments

`--prune-attachments` でローカルに存在しないリモート添付を削除する。デフォルトは削除しない（安全側）。

## 6. FR-25 body_format

### 6.1 設計方針

| 値 | 動作 |
|---|---|
| `html`（デフォルト） | Markdown → HTML 変換して送信 |
| `md` | Markdown のまま送信 |

**理由:**
- eLabFTW は Markdown レンダリング（MathJax 含む）をサポートする
- 数式を多用する場合、HTML 変換すると `$...$` が壊れる
- 既存設定との互換のためデフォルトは `html` を維持

### 6.2 init 時のデフォルト

`esync init` で新規作成する場合は `md` を提案する（`BODY_FORMAT_INIT`）。新規ユーザーには Markdown のまま送信するほうが直感的。

## 7. FR-26 カテゴリ管理

### 7.1 設計方針

- `category` フィールドに ID（数値）または名前（文字列）を指定可能
- 名前指定時は `resolve_category_id()` で API から ID を解決
- push の前にターゲットごとに 1 回 ID を解決し（v1.0.4）、解決できない場合はカテゴリの設定が必要な文書だけを eLabFTW を変更せずにスキップする。本文を更新した後で失敗し、文書が中途半端な状態で止まるのを避けるため
- 一覧 API に出ない（読み取り権限のない）カテゴリは、記事の現在の `category_title` や同じターゲットの別文書から ID を補う（v1.0.2・v1.0.4）
- push 時に `_sync_category()` で設定。失敗はタグと同じく部分失敗として扱う
- pull 振り分け時にもスコアリングに利用

### 7.2 CLI 操作

```bash
esync category list --entity items
esync category show --id 42 --entity items
esync category set "試薬" --id 42 --entity items
```

## 8. テスト設計思想

### 8.1 全体方針

- eLabFTW API への実通信は行わない（全て `unittest.mock` でモック）
- ファイルシステム操作は `pytest` の `tmp_path` を使用
- 各テストは独立して実行可能（状態を共有しない）

### 8.2 API レスポンス形式の揺れへの対応

eLabFTW API のバージョンによって `tags` フィールドの形式が異なる:
- 辞書リスト: `[{"id": 1, "tag": "name"}, ...]`
- 文字列リスト: `["name", ...]`
- パイプ区切り文字列: `"tag1|tag2"`

全形式に対応する正規化処理を実装（v0.4.1 で修正）。

## 9. 3-way マージ（v1.0.4）

### 9.1 基準本文の保存

同期のたびに、eLabFTW の本文を pull と同じ Markdown 形式に変換して `{filename}.base` に、ローカルの本文を `{filename}.synced` に保存する。

**理由:**
- 「競合」で止めるだけでは、両側を手で突き合わせる必要があった
- 前回同期時点を基準にすれば、片側だけの変更を安全に取り込める
- eLabFTW が保存時に本文を書き換えた分（箇条書きの記号、エスケープなど）が、diff に毎回出なくなる

### 9.2 競合マーカー

両側が同じ箇所を変えた場合は git と同じ形式のマーカー（`<<<<<<< ローカル` / `=======` / `>>>>>>> eLabFTW #ID`）で両方を残し、マーカーが残る文書は `push --force` でも送らない。判定には esync が付けるマーカーだけを使い、見出しの下線の `=======` などは競合と扱わない。

**理由:**
- git に慣れた利用者が、そのままの手順で解消できる
- マーカー入りの本文が eLabFTW に公開されるのを防ぐ

## 10. 本文の HTML エスケープ（v1.0.5）

eLabFTW は Markdown 本文の保存時に `>` を `&gt;`、`&` を `&amp;` に書き換え、`<…>` を HTML タグとして削除する。pull・diff・clone ではエスケープを戻す。削除された `<…>` は戻せないため、push 時に検出して警告し、解消するまで「送信待ち」にする（pull で原稿の `<…>` を上書きしない）。`.base` は eLabFTW の本文形式に合わせてエスケープした形で保存し、旧版の基準も読めるようにする。

## 11. 次の操作の案内（v1.0.4）

`status`・`diff`・push の失敗時に、文書ごとに実行できるコマンドを表示する。コマンドはプロジェクトのルートで実行する前提で組み立て、空白や記号を含むパスは単一引用符で囲む（POSIX シェルと PowerShell の両方で 1 つの引数になる形。cmd.exe は対象外）。

**理由:**
- 「競合」「リモート削除」などの状態だけでは、次に何をすべきかが分からないという利用者の声があった

## 12. 実験ノート・リソース間のリンク（v1.1.0〜v1.1.2）

### 12.1 追加のみ

ターゲット設定 `links` は、タグと同じく追加のみとし、既存のリンクや設定から外したリンクは削除しない。外すときは `esync relate remove` で明示する。

### 12.2 張り終えたリンクの記録

張り終えたリンクを `state.json` の `links` に記録し、未記録の ID があれば「送信待ち」にする。

**理由:**
- eLabFTW の画面で外したリンクを、通常の push で勝手に張り直さない
- pull・`esync link` で新しく取得・紐付けした文書にも、次の push でリンクを張れる

リンクの追加だけが必要な文書では、タグ・カテゴリを再適用しない（pull 後のリモートの変更を戻さないため）。

### 12.3 接続先

`relate`・`tag` は各ターゲットの接続プロファイルで送信する。v1.0.x の `tag` は default の接続先で送っており、別サーバーのターゲットでは同じ ID の別の記事を変更するおそれがあった。`--id` 指定時に `-t` が一致しなければ、推測せずにエラーにする。v1.2.0 の修正で、`metadata`・`entity-status`・`verify` も各ターゲットの接続プロファイルを、`category`・`list`・`new` も `-t` で選んだターゲットの接続先を使うようにした。

### 12.4 パスでの指定

`relate` のリンク元（`--from`）・リンク先は、ID の代わりに同期済みの文書のパスで指定できる。push 前の文書、種別の合わない文書、別サーバーの文書、同期後に接続先や種別を変えた文書（保存済みの ID が別の記事を指すおそれがある）は、何も送信せずにエラーにする。`--from` は後続の複数のパスを受け取るため、シェルが展開した glob も使える（v1.1.2）。
