## 1. FR-15 タグ・メタデータ管理

### 1.1 タグ同期方針: 追記のみ

push 時の YAML `tags` 設定は **追記のみ** で動作する。リモートに存在するが YAML に記載のないタグは外さない。

**理由:**
- eLabFTW 上で手動付与されたタグや他システム由来のタグを保護する
- 「完全置換」は破壊的であり、事故コストが高い
- タグを外したい場合は `esync tag remove` で明示的に操作する

### 1.2 メタデータ保全方針

`get_metadata()` は eLabFTW の metadata フィールドが null・不正 JSON・非 dict の場合に空 dict を返す。

**理由:**
- 不正な状態のデータを無理にパースするより、安全なデフォルトを返す方が堅牢
- `metadata set` 時に `get_metadata_raw()` で生データを確認し、読めない場合は警告を表示

### 1.3 タグ同期の best-effort 設計

タグ同期（`_sync_tags`）は本文同期の成功後に実行され、失敗しても本文同期の結果には影響しない。

**理由:**
- タグはメタデータであり、本文の同期が主目的
- タグ API の一時障害で本文同期全体が失敗するのは過剰
- 失敗時は stderr に警告を表示し、debug ログに詳細を記録

## 2. FR-16 ステータス管理

### 2.1 ステータス ID 指定方式

ステータスは eLabFTW のチーム設定で定義される ID で指定する。名前指定は非対応。

**理由:**
- ステータス名はチームごとに異なり、名前→ID の解決にはチーム ID が必要
- シンプルさを優先し、ID 直接指定とした

### 2.2 一括更新の安全策

`entity-status set` は複数エンティティが対象の場合、確認プロンプトを表示する。`--id` で単体指定も可能。

## 3. FR-22 接続プロファイル

### 3.1 設計方針

複数の eLabFTW サーバーや異なるチームアカウントに接続するための仕組み。

**実装:**
- `profiles` セクションに名前付きで接続情報を定義
- 各ターゲットで `profile: <name>` を指定して使い分け
- `elabftw` セクションとの後方互換: `elabftw` は暗黙の `default` プロファイル

**理由:**
- 別チームの eLabFTW にも投稿したいユースケースへの対応
- 既存の `elabftw` セクション形式を壊さない後方互換

### 3.2 CLI 操作

`esync profile add/remove/list` で YAML の profiles セクションを直接操作する。

## 4. FR-23 Pull 自動振り分け

### 4.1 スコアリングロジック

複数ターゲットが存在する場合、リモートエンティティのメタデータとターゲット設定をマッチングする。

| 条件 | スコア |
|---|---|
| `title_pattern` (glob) マッチ | +10 |
| `category` 一致 | +10 |
| `tags` 包含率 | 最大 5 + 特異性ボーナス |

**理由:**
- タイトルパターンとカテゴリは明確な意図の表れなので高スコア
- タグは部分一致でも有用だが、曖昧さがあるため重み付けを抑制
- 全ターゲットに共通するタグは特異性が低いとみなす

### 4.2 --auto フラグ

スコアリングで最高スコアのターゲットを自動選択する。対話プロンプトを省略したい CI/スクリプト向け。

### 4.3 新規ターゲット自動追記

マッチするターゲットが見つからない場合、リモートのメタデータ（entity/tags/category）から新しいターゲット定義を `.elab-sync.yaml` に追記する。

## 5. FR-24 添付ファイル

### 5.1 設計方針

`attachments_dir` に置いたファイルを push 時に eLabFTW にアップロードする。画像（Markdown 中の `![](...)` 参照）とは別枠。

**理由:**
- PDF・CSV・Excel 等を Markdown 本文とは独立して管理したいケースへの対応
- `attachments_pattern` で不要ファイルを除外可能

### 5.2 prune-attachments

`--prune-attachments` でローカルに存在しないリモート添付を削除する。デフォルトは削除しない（安全側）。

## 6. FR-25 body_format

### 6.1 設計方針

| 値 | 動作 |
|---|---|
| `html`（デフォルト） | Markdown → HTML 変換して送信 |
| `md` | Markdown のまま送信 |

**理由:**
- eLabFTW は Markdown レンダリング（MathJax 含む）をサポートする
- 数式を多用する場合、HTML 変換すると `$...$` が壊れる
- 既存設定との互換のためデフォルトは `html` を維持

### 6.2 init 時のデフォルト

`esync init` で新規作成する場合は `md` を提案する（`BODY_FORMAT_INIT`）。新規ユーザーには Markdown のまま送信するほうが直感的。

## 7. FR-26 カテゴリ管理

### 7.1 設計方針

- `category` フィールドに ID（数値）または名前（文字列）を指定可能
- 名前指定時は `resolve_category_id()` で API から ID を解決
- push 時に `_sync_category()` で自動設定（best-effort）
- pull 振り分け時にもスコアリングに利用

### 7.2 CLI 操作

```bash
esync category list --entity items
esync category show --id 42 --entity items
esync category set "試薬" --id 42 --entity items
```

## 8. テスト設計思想

### 8.1 全体方針

- eLabFTW API への実通信は行わない（全て `unittest.mock` でモック）
- ファイルシステム操作は `pytest` の `tmp_path` を使用
- 各テストは独立して実行可能（状態を共有しない）

### 8.2 API レスポンス形式の揺れへの対応

eLabFTW API のバージョンによって `tags` フィールドの形式が異なる:
- 辞書リスト: `[{"id": 1, "tag": "name"}, ...]`
- 文字列リスト: `["name", ...]`
- パイプ区切り文字列: `"tag1|tag2"`

全形式に対応する正規化処理を実装（v0.4.1 で修正）。
