# esync for eLabFTW

VS Code の左端にある esync アイコンから、編集中の Markdown の送信先と、プロジェクト全体の同期状態を確認できます。

## セットアップ

1. elab-doc-sync のリポジトリ直下で `uv tool install --force .` を実行します。`esync --version` が 1.5.0 以降の版を使います。開発中の 1.5.0 には、この拡張が使うオプションがない版もあります。`esync pull --help`・`esync push --help`・`esync mv --help` を確かめ、どれか1つでも `--expect-id`・`--expect-server`・`--expect-entity`（`pull` はさらに `--json`）のいずれかが欠けていれば、この拡張と同じソースから CLI をインストールし直してください。`esync tag --help` に `--expect-article-url`、`esync metadata set --help` に `--edit-stdin`、`esync new --help` に `--list-targets` があることも確かめてください。開発版を使う場合や、メタデータ欄に CLI の再インストールが案内された場合は、拡張と同じコミットの CLI を使用してください。古い版や版を確認できない場合は、ワークスペースを開いたときに警告が表示されます。この確認は `esync.timeoutSeconds` によらず 30 秒で打ち切ります。応答しないという警告が出た場合は、`esync.executable` に指定した実行ファイルに `--version` を付けてターミナルで実行し、応答するか確かめてください。
2. [GitHub Releases](https://github.com/Kosaku-Noba/elab-doc-sync/releases) の該当版の Assets から VSIX を取得します。開発版は下の「VSIX の作成」にある Actions 成果物を使えます。VS Code 1.85 以降のコマンドパレットで「Extensions: Install from VSIX...」を選び、`esync-0.3.0.vsix` を開きます。ソースから使う場合は、先に下の「VSIX の作成」を実行し、`dist/` にできたファイルを選びます。
3. `.elab-sync.yaml` があるディレクトリをワークスペースフォルダーとして開きます。接続先や API キーは CLI と共通です。環境変数を使う場合は、VS Code の拡張ホストからも参照できるようにしてください。

信頼済みのファイルシステム上のワークスペースで、PATH 上の `esync` を使います。別の環境にインストールした場合は、VS Code のユーザー設定 `esync.executable` に実行ファイルの絶対パスを指定できます。リポジトリで `uv sync` 済みなら、その `.venv/bin/esync`（Windows は `.venv\Scripts\esync.exe`）も指定できます。

同期状態や差分の取得は、既定で 120 秒たつと打ち切ります。待ち時間は設定 `esync.timeoutSeconds` で変更でき、0 にすると打ち切りません。差分の取得中は通知の「キャンセル」で中止できます。push では、送信直前に差分を取り直して内容が変わっていないかを確かめます。この確認には同じ待ち時間が適用され、ここで時間切れになった場合はまだ何も送信していません。送信が始まった後は、記事を中途半端に更新しないよう、時間で打ち切らず、キャンセルもできません。CLI の警告やエラーは、時間切れやキャンセルで中止した場合もそれまでに受け取った分を含め、出力「esync」に記録されます。

## 使い方

- Markdown エディタ右上の「この文書の差分を確認」で、差分を左右に並べたタブを開きます。左側は前回の同期時の本文（前回の本文が記録されていなければ eLabFTW の本文、新しい文書なら空）、右側は送信する内容です。右側は差分を開いた時点の内容で、編集はできません。未保存の編集は、保存してから確認できます。本文が変わっていない場合は、画像・添付ファイルや設定の変更だけが送信されるかどうかを通知で知らせます。
- 同期設定のあるフォルダーが複数あり、文書のフォルダーを特定できない場合は、先に同期設定のあるフォルダーを選びます。差分を取得するまでの間は、通知の「キャンセル」で選択画面を閉じて中止できます。
- 複数のターゲットに一致する文書は、送信先を選んで差分を開きます。差分タブの名前には、送信先と、新規作成か既存の記事 ID かが表示されます。右上の「この差分の文書を push」で送信します。本文・参照ファイル・設定などが変わった場合は差分を開き直してください。
- 送信先を区別できないと表示された場合は、`.elab-sync.yaml` でそのターゲットに一意の `title` を付け、差分を開き直してください。
- 左端のノート形の **esync** アイコンをクリックします。上の「開いている文書」には、選択中の Markdown の送信先ターゲット、記事 ID、保存した内容の同期状態が表示されます。「差分を確認」を押すと、その文書の差分タブが開きます。差分タブを表示している間は「差分タブで確認中の内容」に、送信先サーバー、比較の基準、改名前の文書、画像・添付ファイルや設定の変更、警告が表示されます。eLabFTW 側でも本文が変わっている場合は「eLabFTW 側の変更」を押すと、前回の同期時と現在の eLabFTW の本文を別のタブで比べられます。同期状態が「競合」「取得待ち」の文書は、差分タブから push しても送信されません。下の「eLabFTW の変更を取り込む（pull）」の手順で取り込むか、どちらかを採用してから差分を開き直してください。送信先が複数表示される文書は、目的のターゲットを展開して「差分を確認」を押します。改名した文書は、旧ファイル名を「差分タブで確認中の内容」の「改名前の文書」で、引き継ぐ記事 ID を差分タブの名前の `#番号` で確認できます。記事 ID がまだ記録されていない文書では、記事 ID 欄に次のどれかが表示されます。
  - 「確認中…」: 初めて照会している間、改名元の候補（ローカルにない記事）が変わった後に照会し直している間、または前回の記事 ID の照会に失敗して照会し直している間です。最後の場合、改名元の候補が変わっていなければ「照会に失敗（前回取得）」のように前回のエラーも並べて表示します。候補が変わると、この文書が引き継ぐ記事 ID も変わる可能性があるので、前回の ID は表示しません。
  - `#42` のような記事 ID: 照会で、この文書が引き継ぐ記事 ID が判明すると表示します。候補が変わらなければ、照会し直している間もその ID を表示します。前回の push が途中で止まった「同期未完了」の文書では、改名していなくても、その push で作成した記事の ID を表示します。
  - 「未割り当て」: 送信先の記事 ID が決まっていない文書です。改名元の候補がなく、同期未完了でもない文書は、照会せずにこう表示します。候補があっても、照会の結果、引き継ぐ記事がないと判定された場合もこう表示します。未追跡の文書は、push すると新しい記事として作成されます。同期状態が「作成結果不明」の文書は、前回の push で記事が作成済みの可能性があり、このままでは再度 push しても作成をやり直せません。サイドバーの送信先で記事ができたかを確かめ、[途中失敗の復旧](https://github.com/Kosaku-Noba/elab-doc-sync/blob/main/docs/13_MIGRATION_V1.md#途中失敗の復旧)の手順で紐付けるか作成をやり直してください。
  - 「確認できません」: 照会に失敗したか、送信先を一つに絞れなかった場合です。既存の記事がある可能性があるので、併記されたエラーを読むか「差分を確認」で送信先を確かめてください。

  記事を取得できなかった場合も、判明した記事 ID はエラーと並べて表示します。
- **eLabFTW の変更を取り込む（pull）**: 同期状態が「取得待ち」「競合」の文書は、「開いている文書」の「eLabFTW の変更を取り込む」、一覧の行の取り込みボタン、またはコマンド「esync: eLabFTW の変更を取り込む」で、その文書だけを取り込めます。取り込んだ文書の中の記事 URL はローカルリンクに書き換えますが、ほかの文書は書き換えません。取り込む前に、取り込み予定を確かめて確認ダイアログを出します。書き換える送信先は、一覧で選んだ行のターゲット（設定の `title`、または文書ディレクトリで一意に決まる名前）で決まります。コマンドパレットから実行して文書が複数のターゲットに一致する場合や、行を選んだ後も同じ表示名の候補が複数残る場合は、選択画面にその名前と記事種別・記事 ID を表示して選んでもらいます。候補を名前で区別できない場合は操作を止めるので、設定でターゲットに一意の `title` を付けてください。確認ダイアログ（改名した文書の紐付けを移す確認を含む）には記事 ID・接続先・記事種別を表示し、同じ3点を CLI に渡して（`--expect-id`・`--expect-server`・`--expect-entity`）、書き換える直前に紐付けが変わっていないかを照合します。未保存の編集は先に保存します。
  - ローカルを編集していない「取得待ち」の文書は、eLabFTW の内容で更新します。両方で編集した「競合」の文書はマージし、両方で変えた箇所を `<<<<<<< ローカル` ～ `>>>>>>> eLabFTW #42` の競合マーカーで示します。マーカーはエディタの「現在の変更を採用」「入力側の変更を採用」などで解消し、保存してから差分を確認して push してください。マーカーが残っている間は push できません。
  - どちらか一方を採用する場合は、「ローカルの内容で eLabFTW を上書き」（`push --force`）または「eLabFTW の内容でローカルを上書き」（`pull --force`）を選びます。実行前に確認ダイアログを出します。上書きされる側の内容はバックアップに退避されます。ローカルのファイルは `esync restore` で戻せます。バックアップによっては文書のディレクトリ全体が戻り、後から追加したファイルも取り除かれるので、先に `esync restore <バックアップID> --dry-run` で戻る範囲を確かめてください（詳しくは [競合を確認・復旧する](https://github.com/Kosaku-Noba/elab-doc-sync/blob/main/README.md#競合を確認復旧する)）。eLabFTW の本文は `esync restore` で JSON として取り出せるので、確認してから必要に応じて貼り直してください。サイドバーに「復旧待ちのローカル変更があります」と表示されたら、その行をクリックすると `esync backup list` の結果を出力「esync」に表示します。
  - pull はファイル名を eLabFTW の記事のタイトルに合わせます。記事のタイトルが変わっていたり、ローカルで改名していたりすると、取り込んだ後のファイル名が変わります（その場合は通知し、取り込んだファイルを開きます）。
  - 改名した文書は、記事と旧名で紐付いたままです。改名後のファイルで取り込みや上書きを選ぶと、先に `esync mv` で紐付けを改名後のファイルに移してよいか確認し、移してから続けます。紐付けの移動はこの確認で確定し、その後の取り込みの確認で取り消しても、紐付けは改名後のファイルに移ったままです。紐付けを移さずに CLI の `esync pull` を実行すると、旧名のファイルに eLabFTW の本文が書き戻され、改名後のファイルは次の push で新しい記事として作成されるので注意してください。取り込んだ後にもう一度改名して push すると、記事のタイトルも変わります。
- 下の「プロジェクト全体の同期一覧」には「送信待ち」「取得待ち」「競合」などの状態ごとに文書が並びます。ローカルにある文書は、行をクリックすると編集でき、行にポインターを合わせて差分ボタンを押すと差分タブを開けます。
- 開いている Markdown の同期状態は、ステータスバー左の「esync: 送信待ち」のような表示でも確認できます。クリックすると、表示している送信先の差分タブが開きます（送信先が複数あれば選びます）。送信先が複数ある文書は、最も注意が必要な状態と送信先の件数を表示します。同期状態を取得できなかった場合は「同期状態を取得できません（前回: 最新）」のように、取り直している間は「最新（更新中）」のように表示し、前回の状態を今回の状態としては示しません。複数のプロジェクトのうち一部だけ取得できなかった場合や取り直している場合は、代表の状態を今回取得できた送信先から選び、取得できなかった場合は警告アイコンを添えます。送信先の件数には前回取得した送信先も含まれるので、ツールチップや送信先の選択画面で「（前回取得）」と付いた送信先は、今回は確認できていないものとして読んでください。改名した文書は、サイドバーで引き継ぐ記事が分かると「リネーム予定」と表示します。改名前の記事が eLabFTW 側でも変更されていれば「競合」と表示します。保存などで同期状態を取り直した後は、サイドバーで照会し直すまで「未追跡」と表示します。
- Explorer では、取得済みの同期状態に応じてファイルにバッジを付けます。`M` は送信待ち、`↓` は取得待ち、`!` は競合・競合マーカーあり・同期未完了、`D` はリモート削除、`?` は作成結果不明・確認失敗・基準情報なし・その他の状態、`R` はリネーム予定、`U` は未追跡です。送信先が複数ある文書には、最も注意が必要な状態のバッジを付けます。バッジのために eLabFTW へ問い合わせることはないので、サイドバーやステータスバーで同期状態を取得するまでは表示されません。
- パネル右上の更新ボタンで最新の同期状態を取得できます。取得中は前回の一覧が表示されたままになり、「開いている文書」には「同期状態を取得中…」と、前回の状態に「（前回取得）」が表示されます。前回の一覧にない新しい文書や改名した文書も、取得が終わるまでは同期対象外と表示しません。一覧の更新に失敗した場合、エラーの下には前回取得した一覧が表示されます。再試行を始めると、一覧の取得自体に失敗したときのエラーはいったん消え、今回も失敗した時点で再び表示されます。文書ごとのエラー（記事の取得や記事 ID の照会の失敗）は、取り直している間も「HTTP 401（前回取得）」のように前回のものと分かる形で残り、取り直しが終わると今回の結果に置き換わります。記事 ID 欄は、前回の照会で ID が判明していて改名元の候補が変わらなければ、照会し直している間もその ID を表示します。前回の記事 ID の照会に失敗していれば「確認中…」と前回のエラーを、改名元の候補が変わって照会し直す必要がある場合は、前回のエラーを出さずに「確認中…」だけを表示します（最後の候補がなくなった場合は照会せず「未割り当て」になります）。eLabFTW の変更を取り込むには、上の「eLabFTW の変更を取り込む（pull）」を使います。Markdown の保存後と push の後にも一覧を更新します。

## eLabFTW の記事操作

- 記事 ID と前回同期時の接続先を確認できた文書は、同期一覧の外部リンクボタン、または「開いている文書」の「eLabFTW で開く」からブラウザで確認できます。接続先が変わった場合は元の設定に戻すか、目的のサーバー用に別の状態ディレクトリを用意してください。旧形式で接続先の記録がない場合は、サーバー・記事種別・ID を確認してから `esync link <ID> --file <docs_dir からの相対パス> --target <ターゲット>` で同じ記事に紐付け直し、一覧を更新してください。
- 「開いている文書」で「タグ」「関連リンク」「メタデータ」を展開すると、その記事の現在の値を読み込みます。見出しを右クリックして追加し、タグやリンクの行を右クリックして外します。メタデータの行を右クリックすると、そのキーの値を文字列として設定できます。オブジェクトや配列の値は JSON 表記で確認でき、文字列への上書きは中止されます。変更は確認した記事に直接反映されます。編集グループや作成先が表示されない場合は、ターゲットに一意の `title` を付けて更新してください。メタデータの編集中に同じキーが変更された場合も、一覧を更新してやり直してください。値の再取得から保存までの間に他の利用者が更新した場合は検出できません。
- 「テンプレートから新規文書を作成」で、プロジェクト、作成先ターゲット、実験テンプレート、タイトルを選ぶと、作成した Markdown が開きます。ファイル名や配置に専用の `pattern` がある場合は、それに合う相対パスも入力します。同じターゲットで別のディレクトリに同名文書がある場合や、以前の紐付け・作成記録・除外設定がその名前に残っている場合は、別の名前を使ってください。記事として送るには差分を確認して push します。
- 「同期ログを表示」で、選んだプロジェクトの直近20件の記録を出力「esync」に表示します。

## 開発

Node.js 22 以降が必要です（テストに使う `@vscode/test-electron` の要件）。このディレクトリで `npm install` を実行してから、次のコマンドを使います。

- `npm run check`: JSDoc の型注釈を TypeScript で検査します。
- `npm test`: 拡張ホストでテストを実行します。VS Code を自動で取得します。インストール済みの VS Code を使う場合は、環境変数 `VSCODE_EXECUTABLE` に実行ファイルのパスを指定します。画面のない Linux では `xvfb-run -a npm test` で実行します。

## VSIX の作成

Node.js 22.12.0 以降で、このディレクトリから実行します。

```sh
npm ci
npm run package
```

パッケージは `dist/esync-<拡張の版>.vsix` に生成されます。PR では GitHub Actions の Tests 実行画面から成果物 `esync-vsix` をダウンロードし、ZIP を展開してインストールできます。GitHub Release を公開すると、そのタグのコードでテストとパッケージ作成が実行され、成功後に同じ VSIX が Release の Assets に追加されます。
同じ Release でジョブを再実行した際は、同名・同内容の添付ファイルを保持します。内容が異なる場合とアップロードが中断して空ファイルが残った場合は、ジョブのログに理由が表示されます。
